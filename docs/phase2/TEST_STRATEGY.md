# Test and validation strategy

**PLAN ONLY.** No migration, Docker runtime, remote-host test, dependency installation or application test was executed in Phase 2. Source inspection verifies code behavior, not successful execution. The tracked repository currently lacks test sources and package metadata; new test paths below are proposed. All destructive failure injection uses disposable fixtures/VMs, never the existing Contabo host or a customer production database.

## Evidence and result contract

Every check records ID/version, applicability evidence, input/checkpoint/attempt IDs, runtime contract hashes, start/end time, expected/actual summaries, protected evidence references and result: PASS, FAIL, BLOCKED, NOT TESTED, or NOT APPLICABLE. A skipped mandatory check cannot become PASS. NOT APPLICABLE needs evidence such as absence of an installed module and its records; missing adapters are BLOCKED. Reports contain sanitized summaries; sensitive row-level evidence remains in protected job storage. No universal data-correctness claim follows from technical PASS.

Compare each candidate against both its predecessor and CP0's semantic baseline, using reviewed version mappings; this detects cumulative drift across steps. Module renames, business-record transformations and tolerances must be declared before execution. An unexplained difference blocks publication. Rollback is a new restore of the unchanged last verified checkpoint; tests assert that its bytes and manifest remain identical.

## Three validation levels

| Level | Mandatory technical contract | Conditional business contract | Gate |
| --- | --- | --- | --- |
| V1: input/preflight | Verified immutable input digest/type and bounded safe archive; successful restore; actual source/base version; source registry/module/attachment integrity; approved path and runtime provenance; complete per-step addon graph; PG/extension compatibility; storage/mount permissions, space/inodes and exclusive ownership | UoM diagnostics and semantic baseline where installed; accounting/stock baselines where installed; custom modules/external attachment stores require applicable adapters | Publish CP0 only after its source technical checks. Known source-data blockers can be recorded in CP0, but block the affected transition until resolved |
| V2: every version/checkpoint | Actual target version, database accessibility, required models/schema, mapped installed-module closure, no pending states or partial-upgrade marker, stopped writers, matched filestore, full hashes, successful fresh snapshot restore, normal pinned target registry probe and report | UoM conversion checks; accounting and stock invariants for installed modules; approved custom/module-specific checks | All applicable mandatory checks PASS before the ledger advances. Exit 0, archive listing or logs alone cannot pass |
| V3: final/artifact | V2 plus normal target startup on isolated restored copy, core-record/relationship checks, final target and module state, artifact manifest/hash and restore test, successful publication protocol | Full applicable UoM/financial/inventory checks; required custom validations; customer-specific UAT recorded separately | Target checkpoint may exist while packaging fails; no final artifact or COMPLETED state until final gates pass |

Mandatory technical integrity includes database constraints, required table/column/index presence under version adapters, expected model availability and critical relationship checks for migrated records. PostgreSQL constraints alone do not cover all Odoo logical relationships. Define required adapter checks from each supported module's actual source/schema; do not invent universal table layouts or run broad unversioned SQL. Registry validation uses a disposable restore, SQL marker/module checks **before** startup, no upgrade flags/OpenUpgrade patch loading, no cron/HTTP and blocked external egress. Odoo 19 private registry attributes are verified source contracts; 16–18 adapters remain a Phase 3 research/qualification gate.

Business checks are conditional on module applicability but **mandatory once applicable**:

- Accounting: compare posted move totals by company/account/currency and agreed period, debit/credit and company-currency balance, residual/receivable/payable totals, and representative tax/currency results. Preserve reconciliation and transaction identity through reviewed mappings. Compare source and target in equivalent business semantics with explicit currency rounding tolerances. An unbalanced source is a recorded blocker; do not silently correct financial data.
- Inventory: compare physical and reserved quantities by company/product/location/lot/package/owner and canonical UoM, plus valuation totals and cost basis where valuation modules apply. Reconcile internal/transit location treatment and negative stock explicitly. Version-specific adapters must be derived from actual source; raw row counts alone are insufficient and legitimate schema transformations require mappings.
- UoM: compare normalized ratios and actual quantity/price conversions in both directions with and without rounding; validate all used pairs, inactive units, renamed roots and custom bigger/smaller units. Use complete pair coverage in small fixtures, anchor-normalized ratios plus all business-used rounded pairs in large data. No arbitrary tolerance chosen after a mismatch.
- Attachments: map each file-backed attachment to its safe relative `store_fname`, verify existence/size/SHA-256 and Odoo SHA-1 where stored, and verify complete snapshot inventory. Distinguish database-backed `db_datas`, URLs, and external storage. External-store modules need a validated adapter; never treat an unavailable store as empty. Reject traversal/symlinks. Full orphan inventory is reported; approved orphan retention is distinct from missing referenced data.
- Core/custom records: count and semantically compare mapped partners, products, companies and agreed critical documents; verify relationships and permissions relevant to installed/custom modules. Customer-specific workflow UAT can remain a separate acceptance item, clearly marked NOT TESTED, but cannot waive required technical or installed-module integrity gates.

The final package format must be qualified against the intended target import workflow. If supporting Odoo backup ZIP import, derive required metadata and layout from the pinned Odoo backup/restore implementation and test import in isolation; do not assume the current `dump.sql` plus filestore ZIP proves compatibility. Checkpoints remain internal custom-format dumps, independent of export format.

## Test layers and release sequence

1. Unit tests: deterministic state machine, hashing/schema, CLI behavior, path limits, error classification and semantic comparisons. Use a real temporary SQLite database for transactional contracts; fake Docker is appropriate only for orchestration edge cases. Target at least 90% meaningful coverage of critical state/publication/ownership rules where practical; coverage cannot replace fault injection.
2. Local isolated integration: real PostgreSQL/filestore snapshots, Docker resource labels, exact image provenance, registry adapters and crash windows. Use fresh unique resource names and test-owned cleanup. Do not contact the configured remote daemon accidentally: harness checks an explicit disposable daemon identity and refuses unknown contexts.
3. Migration regression: synthetic, noncustomer source fixtures at each supported source, real pinned Odoo/OpenUpgrade runtimes, known-error reproductions and full-chain equivalence. Preserve expected failures on affected revisions as separate regression evidence; only qualified fixes pass release gates.
4. Remote qualification: isolated Ubuntu VM matching verified deployment prerequisites; distinct client filesystem, real SSH, systemd, worker loss, Docker restart and VM reboot. Reboot requires disposable-target authorization in the test environment. Validate backups by restoring to a second isolated host, not by overwriting the original test service blindly.
5. Customer acceptance trial: separately authorized disposable backup, approved module profile and business criteria, restricted data handling, reviewed report and UAT disposition. Never promote synthetic test results to customer readiness.

Split CI into fast PR checks, integration checks on explicitly isolated runners, and expensive migration/remote qualification for release candidates. No customer backups or secrets in public CI artifacts. Existing `.github/workflows/upgrade-test-{ubuntu,macos,windows}.yml` and `publish-pypi.yml` need redesign around the new package and CLI contracts; macOS/Windows can validate the client while Linux qualifies the worker. Publish packages only after required checks; distribution does not imply every runtime profile is qualified.

Measure baseline restore/checkpoint/validation runtime, peak bytes/inodes, log growth and memory using declared fixture sizes; report measurements before setting operational limits. Do not promise universal storage multipliers or time estimates. First release acceptance requires all R1–R8, E1–E8 and D1–D6 applicable to its advertised profile, plus C/H gates. Any skipped remote/full-chain scenario leaves that release capability **NOT TESTED** and unqualified.

## Phase 2 verification boundary

Only documentation completeness, links/evidence consistency and unchanged application-source checks belong to this phase. They cannot demonstrate that the proposed engine, systemd service, data repairs or migration paths work. Implementation and execution of this test plan require explicit Phase 3 approval.
