## Prospective classification rules

The following cover required failure classes without asserting they have already occurred. Each error stores detector/rule version, candidate matches, confidence, stage, exception class, SQLSTATE where present, module/script path, runtime manifest digest, exact exit/signal/OOM evidence and protected log offsets. A text match alone is insufficient to select a data repair. Conflicting or incomplete matches become UNKNOWN.

| Class | Detection/evidence and diagnostic output | Remediation, retry and approval | Regression |
| --- | --- | --- | --- |
| DEPENDENCY_ERROR | Build/import failure plus missing distribution/helper, resolved package versions and step manifest | Correct pinned dependency contract through upstream-first policy; no pip install into a failed runtime. Fresh retry after accepted plan | E3, K003, resolver conflicts and unavailable wheel |
| UPSTREAM_MIGRATION_BUG | Trace to pinned OCA/Odoo script plus minimal reproducer or source proof; compare upstream fix/status | Qualified newer revision or approved patch; human acceptance of plan diff; fresh restore | E2, R7, regression at old/new revisions |
| SOURCE_DATA_CONFLICT | Read-only diagnostics prove violated/ambiguous source conditions; IDs in protected report only | No generic auto repair. Reviewed clone-only resolution with before/after proof | E1, ambiguous root and nonfinite/zero factors |
| SCHEMA_MISMATCH | UndefinedColumn/UndefinedTable/invalid schema, expected schema revision and installed-module map | Establish source lineage/order/addons first; no ad hoc ALTER TABLE. Reviewer chooses correction | E4, missing column/model and spoofed base version |
| MODULE_DEPENDENCY_ERROR | Missing manifest/model, module graph omission, pending states or unresolved dependency closure | Supply compatible versioned modules; never silently uninstall. Reviewer accepts runtime change | E5, missing transitive/Enterprise provider |
| DATABASE_ERROR | SQLSTATE, PG stderr, permissions, restore failure, connectivity/transaction evidence | Transient connection retries allowed only before migration; after data changes, explicit retry from checkpoint after cause cleared | E4, corrupt dump, connection loss, denied restore |
| RESOURCE_EXHAUSTION | ENOSPC/quota/inodes/OOMKilled, actual measurements and reserved estimate | Report needed resource; operator remedies host capacity; no checkpoint deletion for space | E7, OOM and metadata-disk full |
| INFRASTRUCTURE_FAILURE | Docker/SSH/daemon availability, exit code/signals and generation IDs | Bounded transfer/readiness retry before mutation; interrupted migration requires explicit clean resume | E6, R3/R4/R5 |
| CHECKPOINT_ERROR | Missing file, hash/schema/parent/verification mismatch or orphan publication | Block recovery; operator may restore exact backup then revalidate. Never choose older checkpoint automatically | R6, crash windows and manifest tampering |
| UNKNOWN_ERROR | Unrecognized or insufficient/conflicting evidence | Record evidence, stop; manual diagnosis and resolution acceptance required. No automatic retry or repair | E8, deceptive signature in module log |

First release permits no automatic migration rerun. Transport retries are bounded and use the same idempotency key/offset. A human-requested retry is not an authorization to change production or source data. Unknown-error acceptance must identify a concrete disposition and verification plan; a blanket `--force` bypass is excluded.

## UoM resolution design

**Read-only diagnostics:** on the immutable 18 checkpoint's restored diagnostic copy, inspect all categories including inactive UoMs; record category/reference counts, `factor`, `factor_inv` semantics, `uom_type`, `rounding`, active state, relevant XML IDs/provider modules, and linked product/inventory/accounting usage. Include SQL-level rows that ORM active filters might hide. Preserve a semantic conversion baseline and normalized record identities. Do not expose customer names or IDs in general logs. The inspected migration SQL reads legacy columns without filtering inactive rows, so archiving duplicates is not a fix.

**Classification:** one reference with finite positive factors = candidate for normal migration; zero references, multiple non-equivalent roots, missing category, zero/nonfinite/negative factor, unknown XML-ID provider, or contradictory history = BLOCKED. Multiple factor-1 references are algebraically compatible but still semantically ambiguous until a unique approved canonical anchor exists. Odoo 18's uniqueness validation is conditional in `write`; do not infer data lineage from presence of duplicates.

**Normalization eligibility (opt-in design, disabled until tested):** a version-scoped rule may reclassify redundant references on a new 18 working copy only if (a) an approved mapping identifies exactly one canonical anchor independently of row order/lowest ID, (b) all affected units have finite positive factors and reference ratio 1, (c) IDs, product links, all factors and effective rounding semantics remain intact, (d) every XML-ID-owning provider and target migration behavior is understood, (e) an isolated complete 18→19 trial passes pairwise conversions and applicable financial/stock comparisons, and (f) the operator approves the digest of the exact remediation report. Changing factors, merging categories/deleting UoMs, or choosing the first row is outside this rule. If any condition fails, block and require a separately reviewed resolution.

Apply approved rules only after restoring a fresh checkpoint, before OpenUpgrade's step, with source-version APIs and a transaction; record rule version, precondition digest, before/after digest and acceptance. Persist the resolution intent first. If interrupted, discard the working copy and regenerate the plan against the same snapshot; never rerun the operation on unknown partial state. Rollback is restoration of the untouched checkpoint, not inverse SQL. No automatic source/production update exists.

**Conversion proof:** Odoo 18 quantity conversion is proportional to `factor_destination / factor_source`; Odoo 19 to `factor_source / factor_destination` under its new absolute-factor semantics ([18 UoM](https://github.com/odoo/odoo/blob/c35f52004d75c19c296e49e9a99e9b8d4447d67f/addons/uom/models/uom_uom.py), [19 UoM](https://github.com/odoo/odoo/blob/a5447ae78fa15f25e69ce44fd154bf1d2f1e383a/addons/uom/models/uom_uom.py)). Compare semantic ratios against a stable mapped anchor within each original category; do not assume that the global reference/root stays the same (e.g. a target hierarchy may choose a smaller base unit). Check quantities and prices, both directions, rounding on/off at declared tolerance, representative magnitudes and actual used unit pairs. A linear anchor-normalization check can establish all unrounded ratios without quadratic runtime; use exhaustive pairs for small regression fixtures and all business-used pairs for rounded behavior. Reject unexpected cross-category conversions and cycles in target ancestry.

The separate bigger-unit bug requires upstream code correction; normalizing source ratios to accommodate a broken script would misrepresent source data. PR #6054's join gives one reference per SQL row but can assign a unit repeatedly when several references share a category; it does not settle root ambiguity. Until a qualified fix is accepted, mark affected 18→19 profiles blocked. Existing upstream tests use direct `factor` for bigger units and omit duplicate references; add UI-style `factor_inv=24`, empty/single/multiple reference, inactive, export-only XML ID, provider XML ID, and custom-category fixtures.

## Upstream-first decision sequence

For each occurrence: inspect exact runtime SHA for a fix already present → compare a newer verified upstream revision → supported configuration/dependency correction → provable source normalization on a copy → reusable wrapper compatibility rule → explicit version-pinned upstream patch last. Preserve original error and source evidence. Never bypass a required migration script, clear module states, fabricate a missing column/model, or silently edit upstream files. Each resolution must identify tests, approval, scope and checkpoint-based rollback.
