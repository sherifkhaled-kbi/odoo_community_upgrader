# Known issues: UoM 18 → 19

**Research revisions:** application `49c16285eb160b11d8a977bba278bf3a3bc333f1`; OCA OpenUpgrade 19.0 [`bf12c3cee6097145e53efa589b0d99a7e64d6a87`](https://github.com/OCA/OpenUpgrade/commit/bf12c3cee6097145e53efa589b0d99a7e64d6a87); official Odoo 18 [`c35f52004d75c19c296e49e9a99e9b8d4447d67f`](https://github.com/odoo/odoo/commit/c35f52004d75c19c296e49e9a99e9b8d4447d67f) and 19 [`a5447ae78fa15f25e69ce44fd154bf1d2f1e383a`](https://github.com/odoo/odoo/commit/a5447ae78fa15f25e69ce44fd154bf1d2f1e383a). The incident database and full traceback were not available.

## Source-level cause

`CONFIRMED` Odoo 18 stores UoMs in `uom.category`, with `uom_type` and `factor`; its `_check_category_reference_uniqueness` rejects more than one reference unit on normal `create`/`write` ([Odoo 18 UoM model](https://github.com/odoo/odoo/blob/c35f52004d75c19c296e49e9a99e9b8d4447d67f/addons/uom/models/uom_uom.py)). Odoo 19 removes categories and links units into trees via `relative_uom_id`, with `relative_factor`; root units require factor 1 ([Odoo 19 UoM model](https://github.com/odoo/odoo/blob/a5447ae78fa15f25e69ce44fd154bf1d2f1e383a/addons/uom/models/uom_uom.py)). OCA's [pre migration](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/19.0.1.0/pre-migration.py) copies old columns to legacy names and removes a legacy constraint. Its [post migration](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/19.0.1.0/post-migration.py#L7-L58) groups all units by old category, filters **every** old `uom_type == 'reference'` into `old_reference`, and writes that recordset into singular `relative_uom_id` for each non-reference, non-XML-ID unit.

`CONFIRMED conditional defect` If one legacy category contains at least two references and at least one eligible non-reference unit, `old_reference` has length >1. Official Odoo 19 [Many2one `convert_to_cache` lines 329-335](https://github.com/odoo/odoo/blob/a5447ae78fa15f25e69ce44fd154bf1d2f1e383a/odoo/orm/fields_relational.py#L329-L335) raises `ValueError("Wrong value for ...")` for multi-record values. This matches the reported exception mechanism. **Real incident cause remains `NOT VERIFIED`** until a sanitized DB query and traceback confirm that exact category and branch revision. Odoo 18's normal ORM prevents duplicates, so their origin may be old data, import, direct SQL, bypass, or a prior migration; the investigation cannot assign blame without data lineage.

`CONFIRMED` A separate conversion problem exists in the inspected script: it sets `relative_factor = old factor` for `bigger` units, while Odoo 18's `factor` is inverse of the displayed bigger ratio. The result reverses user-created bigger conversions. [Open PR #6054](https://github.com/OCA/OpenUpgrade/pull/6054) (head `5720f589e0760db3584cc19d19105feaf8fa9870`, **open and unmerged** when checked) proposes `1 / factor` for all types and adjusts the UoM test data. It also changes SQL to join each reference row; with multiple references that avoids passing a multi-record set to a Many2one but can assign a non-reference unit to multiple roots in turn. **It is not established as a correct multi-reference repair**, and is not present in the inspected 19.0 branch snapshot. [PR #2666](https://github.com/OCA/OpenUpgrade/pull/2666) merged into **14.0** in 2021 and changes 13→14 UoM data; it is not a 19.0 fix.

`CONFIRMED` The existing [migration fixture](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/tests/data_uom_migration.py) creates one reference per category and writes `factor=1000000` directly for a `bigger` unit; it does not exercise multiple references or the 18.0 UI's `factor_inv` storage path. The [post-migration test](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/tests/test_uom_migration.py) checks selected conversions. The post script also loads [noupdate UoM records](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/19.0.1.0/noupdate_changes.xml) through a [transformation](https://github.com/OCA/OpenUpgrade/blob/bf12c3cee6097145e53efa589b0d99a7e64d6a87/openupgrade_scripts/scripts/uom/19.0.1.0/noupdate_changes-transformation.xml) that suppresses writes to legacy `factor` and most `active` fields. This is separate from the custom UoM loop that fails on ambiguous references.

## Reproduction and additional evidence needed

Use only a disposable copy of the affected 18.0 database. Record the image digest, OCA clone SHA, library SHA, exact traceback, installed module versions, and a count of legacy reference units per category including inactive units. Check affected UoM XML IDs and factor values, then compare before/after conversions for representative units and product/inventory/accounting records. A minimal fixture should contain a category with two reference units plus a non-XML-ID unit, and a separate user-created bigger unit. Do not mutate the customer source database.

Potential directions, **not approved designs**: (1) preflight detects ambiguous categories and blocks with a diagnostic; (2) business owner chooses one reference and reviews conversion semantics on a DB copy; (3) an upstream-reviewed migration strategy handles ambiguity and safeguards all linked records; (4) track PR #6054 for the separate factor inversion and validate its behavior before adoption. No workaround or database change was applied.
